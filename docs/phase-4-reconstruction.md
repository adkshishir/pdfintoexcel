## The two design moves that matter

The algorithm went through three iterations before settling on what works.
Each iteration was forced by the bank-statement fixture (4-column layout
with `(GBP) Amount` / `(GBP) Balance` headers).

### Move 1 — Use word centers (not extents) to find columns

Naive extent-density profile: project each word's `[x0, x1]` interval and
look for valleys. **This fails** on the bank statement because the header
words `(GBP)` and `(GBP)` sit *inside* the visual gaps between body
columns. The extent profile has no zero-density bins anywhere — every gap
gets bridged by a header word.

**Fix:** project each word's *center* point (not its extent). Word centers
form tight clusters at column centers regardless of header bleed. K column
centers → K peaks in the smoothed profile.

### Move 2 — Use peaks for centers, extent valleys for boundaries

After move 1, peak detection found the right number of columns and roughly
the right centers. But picking boundaries as the *midpoint between
consecutive peaks* placed the Description↔Amount boundary at x=303,
slicing through the actual Description column (because the Description
peak landed at x=180 — Description's left edge has the most word centers
since words start at consistent x=152).

**Fix:** between each pair of consecutive center-peaks, scan the *extent*
density profile and pick the bin with minimum extent. This places the
boundary in the middle of the actual visual gap, not at an artificial
midpoint between centers.

These two moves together make the algorithm work on the bank statement
without per-fixture tuning.

## Empirical result on `MonzoBus.pdf`

```
pdf:    24 pages, 6415 word boxes
raw:    23 tables reconstructed
clean:  23 tables retained
```

Compared to Phase 2's digital extractor (which uses a different algorithm
with header-anchored columns):
- Same number of detected tables (23/24 — page 0 is the cover)
- Same headers on every page: `['Date', 'Description', '(GBP) Amount', '(GBP) Balance']`
- Same column structure for body rows (numeric Amount/Balance separated
  cleanly from text Description)
- The reconstructor algorithm also handles the OCR case (digital just
  reuses it via the same WordBox interface)

The output `.xlsx` from the reconstructor and from Phase 2 are essentially
equivalent for this fixture. **The reconstructor's value is that the same
code works on noisy OCR boxes** — Phase 2's header-anchor trick relies on
the header being a clean horizontal line, which OCR can break.

## Validation against scanned PDF

`MonzoBus.scanned.pdf` (24 image-only pages, generated by
`scripts/make_scanned_pdf.py`) is the held-out scanned sample. End-to-end
validation requires PaddleOCR or Tesseract — only available in the worker
container. To verify in Docker:

```bash
docker compose -f infrastructure/docker-compose.yml up --build -d
curl -F file=@MonzoBus.scanned.pdf -F mode=fast http://localhost:8000/api/jobs
# wait ~60s on cold first run (PaddleOCR downloads models), then:
curl http://localhost:8000/api/jobs/<id>     # status: completed
curl -OJ http://localhost:8000/api/jobs/<id>/download
```

The downloaded `.xlsx` should have the same headers as the digital path.
OCR errors will manifest as misspellings or split words in cells, but the
column structure should match.

## Architectural decisions

- **Pure function over WordBox.** Reconstructor takes `(boxes, page_count)`
  and returns `RawTable[]`. No PDF, no I/O, no OCR. This is what makes it
  testable on synthetic inputs and source-agnostic (digital + OCR same).
- **One table per page in v1.** Multi-table-per-page handling needs a
  segmentation step (e.g. detect large vertical gaps in row clusters)
  that isn't justified by current fixtures. Punted to a future phase.
- **No vertical merged cells.** `row_span` always 1. Row-spanning cells
  would need ruling-line detection on the rendered image. Punted.
- **Constants live in one block at the top of `reconstructor.py`.** Every
  tunable has a default justified in `docs/table-reconstruction.md` §10
  with the why-this-default reasoning.

## What Phase 4 deliberately leaves unfinished

- **"This isn't a table" filter.** Page 0 of `MonzoBus.pdf` (cover/summary)
  produces a plausible-looking 2-column table from layout coincidence. The
  reconstructor doesn't refuse to emit it. Phase 5's cleaner should detect
  and drop "tables" whose headers look like prose (mostly mixed case, no
  short labels) or whose rows have wildly heterogeneous structure.
- **Multi-line cell merging.** Same issue Phase 2 has — wrapped descriptions
  show as separate rows. Phase 5.
- **Cross-page table merging.** The bank statement is logically *one* table
  across 23 pages but exports as 23 sheets. Phase 5.
- **Real OCR validation against `MonzoBus.scanned.pdf`.** Local environment
  has neither tesseract binary nor paddleocr model weights. Validation has
  to happen in Docker. The dry-run CLI proves the algorithm works on
  pdfplumber word boxes (a clean substitute for OCR boxes for digital text).
- **Image-feature ruling-line detection.** Would help on tables with faint
  borders. Phase 5+.
